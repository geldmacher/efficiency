# RTK Evidence Interpretation

Use this reference whenever RTK history, `rtk gain`, or filtered output is used to assess efficiency or justify a setup or filter decision.

- Treat RTK `Input`, `Output`, `Saved`, and `Save%` as estimates of raw versus filtered shell-output volume. RTK derives the token figures from output size; they are not provider-billed tokens, whole-session input, or task cost.
- Gain rates from RTK 1.0 onward are not 1:1 comparable with 0.x rates. From 1.0, `rtk gain` excludes very large outputs from the headline rate. Cite the RTK version with any rate.
- When the installed RTK is 1.2.0 or newer, a windowed `rtk read` (`--max-lines`, `--head-lines`, or `--tail-lines`) uses that same window as the baseline. The unread remainder is not a saving. A recorded saving is only the filter's reduction inside the window. A read without a window still uses the whole file as the baseline. Numbered `rtk read -n` separates the line number and the text with a tab, as `cat -n` does; that tab is formatting. A plain read that is not valid UTF-8 is recorded as the raw bytes that were shown. These rules describe RTK 1.2.0's tracker. The v1.2.1 tree does not change them. This reconciliation did not run `rtk read`.
- When the installed RTK is 1.2.0 or newer, `total_time_ms` and `avg_time_ms` in the summary, the daily, weekly, and monthly breakdowns, and the JSON and CSV exports include filtered commands, including a filter that emits no output. They omit passthrough, fallback, bypass, proxy, and stored labels that unambiguously end in `(passthrough)`. Those omitted durations are the wrapped process's lifetime, which can be a whole session for an interactive TUI. A dash in the per-command time column means the row is untimed. Rows stored through 1.1.0 as ordinary `rtk curl` for a binary response, or `rtk git show` for raw blob bytes, stay in the timed totals because those labels are ambiguous. A timed total is filtered-command execution time. It is neither RTK-only overhead nor provider time. The v1.2.1 source still omits those rows. This reconciliation did not run `rtk gain`.
- `rtk cc-economics` monthly figures are ccusage provider-usage aggregates. When the installed RTK is 1.2.0 or newer, a month sums the per-project rows ccusage emits for that month. That sum is separate from RTK `Saved` and `Save%`, and it is still not whole-task cost evidence. The v1.2.1 tree does not change this sum. This reconciliation did not run `rtk cc-economics`.
- When the installed RTK is 1.2.1 or newer, command, parse-failure, and hook-decision rows are pruned on a later write to `tracking.history_days`. The default is 90 days. A non-positive value uses 90. A `[tracking]` section that omits `history_days` fails to parse, and that same default is used. A window that cannot be subtracted from the current time keeps every row. `rtk gain` and `rtk gain --history` then describe the retained window. A missing older row can be retention, not evidence that the command never ran. This reconciliation did not run a cleanup.
- When the installed RTK is 1.2.1 or newer, the default text `rtk gain` on a terminal may end with one dim line, `Across a team? Spend by team and person, budgets, audit: pro.rtk-ai.app`. It is printed only when stdout is a terminal, the summary is the default text view, the oldest stored command is at least 7 days old, and the line has not been printed in the last day. JSON, CSV, a pipe, an empty history, and the daily, weekly, and monthly views do not include it. `display.pro_hint = false` or `RTK_PRO_HINT=0` turns it off. The line has no opt-out reminder. It is not `Saved`, `Save%`, or a command row. The age reads the stored timestamp as RFC 3339, or as `YYYY-MM-DDTHH:MM:SS` or `YYYY-MM-DD HH:MM:SS`. A missing or unreadable timestamp counts as today, so the line stays off. This reconciliation did not run `rtk gain`.
- When the installed RTK is 1.2.1 or newer, a tracking migration that cannot run leaves `rtk gain` successful and shows the history the file already has. Stderr says `rtk: tracking database was not upgraded:`. That sentence is not part of the JSON report, and the failed step is not stamped. Do not treat the warning as an empty history or as a failed identity check. This reconciliation did not run `rtk gain`.
- Keep four evidence classes distinct:
  - **Execution coverage:** `rtk gain --history` or equivalent host evidence shows that RTK executed for a command.
  - **Shell-output reduction:** RTK estimates how much command output it removed.
  - **Contributor concentration:** absolute estimated reduction and share of the scoped total identify which commands materially contribute. Do not rank usefulness from average percentage alone.
  - **Whole-task net effect:** changes in provider tokens or cost, agent turns, and result quality remain `unverified` without comparable paired observations for the same task, host, model, effort, and relevant environment.
- State whether evidence is global, project, session, or task scoped; cumulative or same-session; and attributable to Cursor, Codex, another host, mixed hosts, or an unknown host. Never attribute mixed or cumulative data to one task or host.
- Keep host truncation, context-cache pricing, commands that bypass RTK, retries, and re-reads outside the measured claim unless direct evidence covers them. A large output reduction may be useful, but it cannot establish whole-task savings by itself.
- For comparative cost claims, distinguish a single paired observation from a repeatable effect. Account for run-to-run variation, repetitions, and failed or excluded runs in both conditions; report failures rather than silently dropping them from the comparison. Use available evidence first and recommend further measurement only for a specific unresolved decision. This guidance does not authorize a benchmark or provider calls.
- When a filter or setup decision is needed, prioritize material absolute contributors and semantic safety. Small or zero reductions are not automatically harmful, and high percentages on rare commands are not automatically valuable.
- Do not persist machine-specific history totals in plugin guidance, fixtures, or product claims. Do not add telemetry or a background benchmark to obtain them.
