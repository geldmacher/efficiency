# Install new Release from repo

Install the latest stable release from `geldmacher/efficiency` for colleagues using Cursor, Codex, or OpenCode 2.1.2. Read [the installation procedure](../../docs/installation.md) when prerequisite, first-installation, conflict, or recovery details are needed. Use [human communication](../efficiency/references/human-communication.md) for the result.

1. Resolve the invoking harness from explicit session context or the user's requested target. If uncertain, ask which harness to install into. The presence of several apps is not host selection. OpenCode means `@opencode/cli` 2.1.2, not the `opencode-ai` 1.x package. When an older installed copy of this skill names only Cursor and Codex, follow the selected release tag's installation guide for the host list. Other Agent Plugins clients have no supported release archive; explain this limit without writing host files.
2. Locate [the bundled installer](scripts/install-release.mjs) relative to this skill, even when it runs from an installed cache or an unrelated working directory. Check Node.js 22 or newer. No Git checkout, GitHub CLI, npm installation, or external plugin is needed for the plugin installation. RTK is optional; its companion check uses the bundled [RTK lifecycle](../rtk-setup/references/lifecycle.md).
3. Download and verify once with `node <absolute-skill-directory>/scripts/install-release.mjs --host cursor --download-dir <new-temporary-directory>`, substituting `codex` for Codex or `opencode` for OpenCode. The helper creates that new directory and refuses an existing one. Preview with the same helper and `--host cursor --release-dir <downloaded-directory> --dry-run`. Both preview and installation use these exact retained release bytes. Follow the active harness's shell/RTK conventions; RTK is optional for colleagues. For OpenCode, the helper merges only Efficiency's `skills` entry and installs only Efficiency command files. It keeps the original bytes of `opencode.json` and those command files in memory only. If a write in the same run fails, it rewrites those files from that memory and does not copy them to disk. A second run that changes nothing does not write.
4. A request to install or update authorizes this plugin's normal installation. After a successful preview, run the same installer with `--release-dir` and without `--dry-run`; do not ask again for ordinary installation permission. An inspection or preview request authorizes only the download and preview. Native sandbox approvals remain applicable. Clean up only the temporary download directory created for this invocation after the result and recovery evidence are retained.
5. If the preview reports `replacement_requires_approval`, show the installed and selected versions and the reason. Only an explicit decision to replace that identified installation permits `--replace-existing`. That replacement removes the previous plugin directory and does not retain a copy. Never use that flag merely to bypass a failed run. Stop on identity, checksum, archive, path, marketplace, cache, or OpenCode command collisions; report what changed before retrying. Rollback means installing an older GitHub release. Uninstall removes only Efficiency's OpenCode entries.
6. Report the selected release, harness, whether files changed, native installation status, and the one next activation action. `prepared` means Codex still needs its native install step; `installed` verifies the recorded on-disk/native boundary, not live skill discovery. For OpenCode, `installed` means the package, skills registration, and Efficiency commands are on disk. A no-op does not require reloading unchanged source, but never upgrades unknown activation to verified. A failure after the plugin directory is replaced stops and reports; recover by installing an older GitHub release.
7. After successful plugin installation/update (including a no-op), run `node <absolute-plugin-directory>/skills/rtk-setup/scripts/rtk-lifecycle.mjs inspect`. Use the newly verified package's helper if the invoking older package lacks it. Report RTK's installed/latest version and state. If RTK is absent, offer first installation plus integration through [rtk-setup](../rtk-setup/SKILL.md); if an update is available, offer the update plus integration verification through [rtk-update](../rtk-update/SKILL.md). A request for this plugin's update alone is not RTK authorization. Only explicit acceptance starts the selected RTK procedure. A decline causes no RTK/configuration changes. Unknown identity, pins, newer binaries, or lookup failures get an explanation and concrete next check. Keep successful plugin installation usable if this optional check or subsequent RTK step fails; report the two outcomes separately.

Use the helper's normal host installation path. Do not rebuild releases, publish, modify other plugins, delete caches, trust prompts, or restart apps as part of this skill. Global RTK configuration changes belong only to the explicitly accepted RTK companion procedure; ordinary plugin installation does not alter global guidance. Explain host-required reload, trust, enablement, or Plugins Directory actions to the user. Complete discovery verification only after observing it in the changed host or a fresh task.
