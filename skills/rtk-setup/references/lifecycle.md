# RTK installation and stable updates

The dependency-free [lifecycle helper](../scripts/rtk-lifecycle.mjs) requires Node.js 22+. Resolve it relative to this skill, including from installed caches. Follow the active host's shell conventions; if RTK is absent, use Node directly. Use the official [RTK installation documentation](https://github.com/rtk-ai/rtk/blob/develop/docs/guide/getting-started/installation.md) and [stable releases](https://github.com/rtk-ai/rtk/releases/latest). Never use plain `cargo install rtk`: that name can refer to Rust Type Kit.

1. Run `node <skill-directory>/scripts/rtk-lifecycle.mjs inspect`. This reads the active PATH, `rtk --version`, `rtk gain --help`, package-manager ownership, and GitHub's latest non-draft stable release. It reports `executable` (RTK's invocation path), `binary` (its canonical identity path), `installed_version`, `latest_stable_version`, `identity`, `state`, `manager`, issues, and a positive development `source_context` when present. Failed or rate-limited network/metadata checks leave the target unknown; report the limitation and retry only when appropriate. Do not infer a version from memory or install/update on an unknown result.
2. For `absent` or `update_available`, offer the indicated installation/update and the requested host's integration. Show a preview with `node <skill-directory>/scripts/rtk-lifecycle.mjs preview --target <latest-stable-version>`. Retain the exact JSON in a new temporary file for apply. Show the target version, manager, command, affected binary location, and separate integration/configuration impact. An explicit request for this RTK installation/update already authorizes the proposed ordinary change; a plugin update or inspection does not. A decline ends the companion step without native changes.
3. After authorization, run `node <skill-directory>/scripts/rtk-lifecycle.mjs apply --preview <retained-preview.json>`. It re-inspects before applying, recomputes the command, and refuses changed binary, invocation path, version, manager, catalog, or target. It verifies the resulting binary path, Rust Token Killer identity, version, and owner. A package-manager failure or a different resulting version is a failure; do not claim successful installation from exit code alone. A Homebrew `prepare` preview registers only the missing official tap from `https://github.com/rtk-ai/homebrew-tap`. Show this source-registration impact before apply. `status: prepared` means the tap was registered and RTK is still absent. Examine the returned `next_preview`, retain it as a new preview file, and apply its installation command only when it is an allowed `install` for the same target. The accepted RTK installation covers this ordinary continuation; no repeated permission question is needed, but native approvals still apply. If the target changed, the catalog differs, a pin/hidden installation appears, or lookup fails, report the partial preparation and re-inspect rather than guessing, switching managers, or installing unpreviewed bytes. Report any newly registered tap retained after a failed continuation; never untap shared state automatically.
4. Preview and complete the authorized [Cursor](cursor.md) or [Codex](codex.md) integration separately. Back up affected existing files before native init, preserve unrelated hooks, tracking/environment/sandbox settings and user guidance, and retain recovery paths. For Cursor, a setup dry-run may touch Claude files; do not refresh unrelated hosts merely to record an update. Use a fresh actual host task only within the authorized runtime/cost scope. Processor success leaves live activation unverified.
5. If `source_context.reconciliation_required` is true, complete [source maintenance](source-maintenance.md), even for `current`/`unchanged`. The helper deliberately reports source reconciliation as pending and integration as unverified: an agent must examine the actual source/host evidence. Binary success with unfinished integration or reconciliation is a partial result. In a release installation, preserve packaged skills and report compatibility findings for a future release.

Homebrew requires proven `rtk-ai/tap/rtk` ownership, matching installed path/version, no pin, and a local stable formula matching the GitHub target. Read-only checks disable Homebrew auto-update. With RTK absent, existing Homebrew retains preference even if its RTK tap is missing or catalog lookup fails. A read-only `brew tap` listing identifies the missing tap; it is never registered by inspection or preview. If the catalog is stale, report that and preview any explicitly requested catalog refresh separately, then re-inspect; never silently upgrade a different formula version. Cargo requires the official Git source and existing Cargo binary location; updates retain explicit stable tags and use `--locked`. Invoke its discovered `cargo` path without resolving that command symlink, so rustup retains proxy dispatch. Canonical paths serve ownership checks. Branch/development installs are retained. Winget uses exact `rtk-ai.rtk`, checks installed path/identity and pins, requests the explicit version, and verifies its installer URL points to the official release. Do not accept source agreements or override pins silently. Windows execution remains unverified until tested there.

First installation chooses an already present Homebrew on macOS/Linux, Winget on Windows, otherwise an existing Cargo toolchain. It never installs a package manager/toolchain. Manual, unknown, pinned, hidden-from-PATH, prerelease, or newer binaries get concrete instructions and no automatic replacement or downgrade. Do not switch managers as a shortcut.

For an offline repeat against previously retained official release metadata, `--release-metadata <file>` accepts the GitHub response JSON. This skips a fresh online lookup and must be disclosed; the file's structure is validated, but it is not authenticity or freshness proof. The repository verifier uses this option with explicit fixtures and isolated tool doubles. Ordinary internet update checks use the live API.

Keep plugin and RTK results separate. An RTK failure never undoes a successful plugin update. Clean up only this invocation's preview/metadata files after retaining necessary evidence; avoid background telemetry, watchers, automatic paid runs, cache deletion, or app restarts.
